\# Engineering Guide



\## Implementation boundary



Trace the workflow from the point where an agent produces a tool request through validation, authorization, execution, result validation, and outcome recording.



Do not assume that an agent's tool request is trustworthy merely because it was generated by an LLM.



\## Recommended code-tracing sequence



1\. Find the tool registry or tool definitions.

2\. Identify how the agent selects a tool.

3\. Trace tool-name and argument validation.

4\. Trace authorization and policy checks.

5\. Identify the exact execution boundary.

6\. Identify every externally visible side effect.

7\. Trace result parsing and validation.

8\. Trace execution-status and audit recording.

9\. Trace timeout and exception handling.

10\. Trace retry, idempotency, reconciliation, and recovery paths.

11\. Inspect tests covering successful, rejected, failed, and repeated execution.



\## Tool registration



Verify that:



\- only intended tools are registered;

\- tool names are uniquely resolved;

\- tool metadata accurately describes the operation;

\- unavailable tools fail explicitly;

\- dangerous or side-effecting capabilities are identifiable.



\*\*Must not happen:\*\* arbitrary or unregistered operations should become executable because a tool name was supplied dynamically.



\## Request validation



Validate before execution:



\- tool identity;

\- required arguments;

\- argument types;

\- allowed values;

\- resource identifiers;

\- operation-specific constraints.



Validation should occur before any protected side effect.



\*\*Must not happen:\*\* malformed input should reach the side-effecting implementation.



\## Authorization



Authorization should be evaluated for the actual requested operation, not merely for access to the general tool.



Trace:



\- requesting identity;

\- agent identity or execution context;

\- requested operation;

\- target resource;

\- applicable permission or policy;

\- authorization decision.



\*\*Must not happen:\*\* a caller should not obtain broader permissions by selecting a more capable tool.



\## Side-effect boundary



Identify the exact line or function where the operation can change state.



Examples include:



\- database writes;

\- file changes;

\- message sending;

\- API mutations;

\- resource creation or deletion;

\- financial or entitlement changes.



Document the preconditions that must hold before crossing this boundary.



\## Idempotency and duplicate execution



For operations that may be retried, determine whether duplicate execution is possible.



Inspect:



\- idempotency keys;

\- unique constraints;

\- transaction boundaries;

\- request identifiers;

\- deduplication records;

\- safe retry conditions.



\*\*Must not happen:\*\* a timeout or retry must not silently perform the same business side effect twice.



\## Result validation



Treat tool output as untrusted input.



Verify:



\- expected result shape;

\- status;

\- required fields;

\- error state;

\- execution identity where relevant;

\- consistency with the operation that was requested.



\*\*Must not happen:\*\* a malformed or failed result should not be promoted to successful execution.



\## Failure handling



Trace each failure boundary separately:



\- validation failure;

\- authorization denial;

\- unavailable tool;

\- timeout;

\- tool exception;

\- malformed result;

\- downstream failure;

\- uncertain completion.



The implementation should distinguish a confirmed failure from an operation whose completion is unknown.



\## Uncertain execution



A timeout does not necessarily prove that the tool did not execute.



For side-effecting operations, inspect whether the system can:



1\. determine execution status;

2\. safely retry;

3\. reconcile the operation;

4\. surface an unresolved state.



\*\*Must not happen:\*\* blindly retrying an operation whose first execution may already have succeeded.



\## Observability



Execution records should make it possible to understand:



\- which tool was requested;

\- whether validation passed;

\- whether authorization passed;

\- whether execution started;

\- whether a side effect was attempted;

\- whether execution succeeded or failed;

\- whether the final state is uncertain.



Avoid recording secrets or sensitive tool arguments unnecessarily.



\## Security and isolation



Review whether:



\- tool permissions follow least privilege;

\- resource identifiers are authorized;

\- one user's or tenant's resources cannot be accessed by another;

\- tool arguments cannot bypass policy checks;

\- sensitive results are not unnecessarily exposed to the agent.



\## Testing expectations



Tests should cover at minimum:



\- valid execution;

\- unknown tool;

\- invalid arguments;

\- denied authorization;

\- side-effect protection;

\- timeout;

\- tool exception;

\- malformed result;

\- duplicate request;

\- retry;

\- uncertain execution;

\- recovery or reconciliation.



Prefer tests at the narrowest level that proves the relevant invariant, supplemented by integration tests for important side effects.



\## Evidence rule



When reviewing an existing codebase, cite concrete files, symbols, tests, configuration, or runtime evidence.



Do not claim that authorization, idempotency, retries, audit logging, or recovery exists unless the implementation provides evidence for it.



\## Review questions



Before approving an implementation, answer:



1\. What exact operation can the agent cause?

2\. What validates the request?

3\. What authorizes the operation?

4\. Where does the side effect occur?

5\. How is duplicate execution prevented?

6\. What happens after a timeout?

7\. How is the result validated?

8\. How is an uncertain outcome recovered?

9\. What evidence is recorded?

10\. Can one execution context affect another user's or tenant's resources?

HIGH · STRONG EVIDENCE

1. Timed-out Python executions keep the local runner busy until the code finishes

When Python code exceeds the configured timeout, the local executor raises a timeout error but keeps waiting for the submitted code to finish, so the agent run stays occupied instead of being cut off.

Trigger

When a caller submits Python code that runs longer than the configured timeout through the local executor entrypoints, the timeout path is activated.

What the code does

The timeout wrapper runs code in a worker thread and raises a timeout error when the wait expires, but the worker is not stopped and the call path remains occupied until that worker finishes; LocalPythonExecutor and PythonInterpreterTool both route caller code through this wrapper.

Business rule

Configured execution time limits are expected to halt overlong local code runs so the restricted executor returns control promptly instead of continuing the timed-out work.

Basis: EXPLICIT

Business downside

Runaway or intentionally slow snippets are not cut off at the promised timeout boundary, delaying completion of code-based agent runs.

Impact

Immediate outcome
A timed-out code run still occupies the local execution path until the submitted code naturally exits.
Affected party or asset
agent runtime sessions and the local code execution slot
Scale mechanism
Each timed-out invocation retains its execution slot until the underlying code finishes, so repeated overlong submissions accumulate occupied runs.
Detection difficulty
The caller receives a timeout error, which hides that the execution path remains busy after the timeout condition is reported.
Reversibility
The condition clears only after the submitted code finishes or the process is terminated.

How the code reaches the outcome

  • PythonInterpreterTool.forward and LocalPythonExecutor.__call__ both pass caller-supplied code into evaluate_python_code.
  • evaluate_python_code wraps its execution function with timeout(timeout_seconds) when a timeout is configured.
  • The timeout decorator submits the work to a ThreadPoolExecutor and raises ExecutionTimeoutError when future.result times out.
  • The decorator documentation states the timed-out thread continues running until completion, and this path provides no stop or cancellation step before unwinding.
  • As a result, the timeout signal does not cut off the underlying work, so the local execution path remains occupied until that work exits.

What to change

Ensure configured timeout enforcement returns control promptly and does not leave timed-out local code occupying the execution path.

Acceptance check

Given A caller submits Python code through the local executor with a 1-second timeout and the code runs longer than 1 second.
When The timeout threshold is exceeded during execution.
Then The call returns promptly and the submitted code no longer occupies the local execution path.

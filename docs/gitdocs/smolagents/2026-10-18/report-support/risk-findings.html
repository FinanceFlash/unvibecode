Business flaws

HIGH · STRONG EVIDENCE

1. Timed-out executions keep changing shared interpreter state

When a local execution exceeds its timeout, the timed-out code continues running against shared state and later runs reuse that altered state.

Trigger

A caller runs code through the stateful local executor and the code exceeds the configured timeout.

What the code does

When the time limit is reached, the submitted code continues running in a worker thread against the same shared state object after the timeout boundary.

Business rule

Once a local execution hits its configured time limit, that execution must stop changing the shared execution state used by later runs.

Basis: EXPLICIT

Business downside

Later runs use stale variables and logs from work that already timed out, so the timeout no longer contains the failed step.

Impact

Immediate outcome
A timed-out execution keeps appending logs and variables to the shared interpreter state after the timeout boundary.
Affected party or asset
Shared agent execution state and subsequent local code runs
Scale mechanism
Any reused executor instance that times out carries post-timeout mutations into the next execution.
Detection difficulty
High because the caller sees a timeout while the state changes happen afterward.
Reversibility
Recovery requires discarding or reinitializing the executor state.

How the code reaches the outcome

  • LocalPythonExecutor.__call__ passes its persistent self.state into evaluate_python_code for each execution.
  • evaluate_python_code executes submitted code against that state and stores print output inside the same state object.
  • When timeout_seconds is set, evaluate_python_code wraps execution with timeout().
  • timeout() submits the work to a thread and documents that a timed-out thread continues until completion, so the shared state object can keep changing after the timeout boundary.

What to change

Timed-out executions stop mutating shared interpreter state and cannot influence later executions.

Acceptance check

Given a reused local executor with timeout_seconds set and shared execution state
When one submitted code action exceeds the timeout and a later action runs on the same executor instance.

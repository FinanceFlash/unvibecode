Summary

Two payment-integrity flaws are established. CyberSource maps explicitly rejected gateway outcomes into successful payment states, and Sagepay callback processing updates whichever waiting payment object is supplied without binding the callback to that payment.

CRITICAL · STRONG EVIDENCE

1. CyberSource rejection results are committed as successful payments

When CyberSource returns listed reject or verification-failure reason codes, the provider records the payment as CONFIRMED or PREAUTH and uses the success path.

Trigger

A CyberSource charge or payer-auth callback returns a mapped reject or verification-failure reason code.

What the code does

The mapped reject branches set a reject-oriented fraud result and then call the success-state helper, which sets captured amount and moves the payment to CONFIRMED or PREAUTH.

Business rule

A payment outcome that the gateway explicitly marks as rejected or failed by fraud or verification checks must not be committed as a successful payment.

Basis: UNIVERSAL INTEGRITY

Business downside

Rejected or suspicious transactions enter the successful payment workflow.

Impact

Immediate outcome
The payment record carries a paid or preauthorized status after a reject-coded gateway result.
Affected party or asset
Payment records, buyer checkout outcome, and downstream paid-order handling
Scale mechanism
Every listed reject branch uses the same confirm helper and the callback path redirects confirmed or preauthorized payments to success.
Detection difficulty
The record keeps a separate fraud flag, so ordinary checks that trust payment status still treat the transaction as paid.
Reversibility
Manual payment-state correction and downstream order correction are required after the record is committed.

How the code reaches the outcome

  • CyberSource reason-code handling has explicit branches for reject-oriented outcomes such as decision-manager rejection and verification failures.
  • Those branches call the same helper that records captured amount and moves the payment to CONFIRMED or PREAUTH.
  • The callback completion path treats CONFIRMED and PREAUTH as success and redirects to the success URL.

What to change

Gateway reject outcomes must never commit a payment into a successful lifecycle state.

Acceptance check

Given a CyberSource response carrying FRAUD_MANAGER_REJECT or another listed reject or verification-failure reason code
When the provider maps that outcome during charge or callback processing.
Then the payment must not be marked CONFIRMED or PREAUTH and the success path must not be used.

HIGH · STRONG EVIDENCE

2. Sagepay callbacks update whichever waiting payment is supplied

Submitting a valid Sagepay callback against a different waiting payment changes that payment because the callback is not matched to the payment before status changes.

Trigger

A Sagepay callback is processed for a waiting payment object.

What the code does

The callback handler decrypts the callback, reads the returned status, and confirms or rejects the supplied payment based on WAITING state and returned status without validating that the callback belongs to that payment.

Business rule

A gateway callback must be bound to the same payment it is reconciling before that payment is confirmed or rejected.

Basis: UNIVERSAL INTEGRITY

Business downside

A different payment record is reconciled with the wrong gateway result.

Impact

Immediate outcome
The selected waiting payment is confirmed or rejected even when the callback belongs to a different payment.
Affected party or asset
Payment records and checkout outcome routing
Scale mechanism
Any valid Sagepay callback processed with the wrong waiting payment object follows the same status-change path.
Detection difficulty
The resulting update looks like an ordinary callback reconciliation unless callback-to-payment linkage is audited.
Reversibility
Manual state correction is required for the misapplied payment and any downstream order actions.

How the code reaches the outcome

  • Sagepay checkout creation is payment-specific and writes payment identity into the outbound request payload.
  • The callback handler decrypts the return payload and branches only on the supplied payment's WAITING state and the returned Status value.
  • No callback-to-payment validation is performed before the supplied payment is confirmed or rejected.

What to change

Gateway callbacks must be bound to the intended payment before any payment state transition is committed.

Acceptance check

Given a valid Sagepay callback and a different waiting payment object
When callback processing runs for the supplied payment
Then the provider must reject the mismatch instead of confirming or rejecting that payment.

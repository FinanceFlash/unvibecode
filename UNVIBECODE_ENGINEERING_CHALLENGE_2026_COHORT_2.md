# ✅ Both Tracks Start the Same Way

## 1. Install UnvibeCode

```bash
pip install unvibecode
```

## 2. Choose a repository

Use either:

- your own public repository, or
- any public open-source repository downloaded from GitHub.

Example: download the public [Flask repository](https://github.com/pallets/flask), extract it locally, and analyze that folder.

## 3. Run UnvibeCode

```bash
python -m unvibecode review --repository "/path/to/repository"
```

Windows example:

```bash
python -m unvibecode review --repository "D:\\flask"
```

No activation key or OpenAI API key is required.

For setup and output details, read the [UnvibeCode README](https://github.com/FinanceFlash/unvibecode).

## 4. Review the output critically

Review outputs such as:

- Business Workflow Map
- Connected Code Map
- Business Risk Findings
- Complete Repository Context

Do not assume every generated finding is correct. Compare important claims with the actual repository.

That real usage is the starting point for both tracks.

# 🔧 Track 1 — Engineering Issue

Track 1 is for participants who want to contribute through **technical feedback and product improvement**.

After running UnvibeCode, identify one focused improvement, concern, or bug.

Good examples include:

- a workflow or dependency inferred incorrectly,
- a business-risk finding that needs stronger evidence,
- a confusing or incomplete output,
- an installation or platform issue,
- a missing engineering pattern, or
- a runtime/dependency limitation.

Before creating an issue, check the [existing issues](https://github.com/FinanceFlash/unvibecode/issues) to avoid duplicates.

Use this structure:

```md
Title: [Issue] Short description

## Problem
What is missing, incorrect, broken, or confusing?

## Evidence
What did you observe in the repository or UnvibeCode output?

## Suggestion
What should be changed or improved?

## Example
Add a command, file reference, link, or screenshot if useful.
```

**Do not create a pull request for this challenge. Only GitHub issues are accepted for Track 1.**

A small, technically well-supported issue is better than a large, generic feature request.

# 🎥 Track 2 — Technical Community Content

Track 2 is for participants who want to demonstrate **technical understanding, communication, and community contribution**.

You must still install and use UnvibeCode first. Your post or video should come from something you actually observed, understood, questioned, or learned while analyzing a repository.

You can publish on:

- **Reddit**
- **LinkedIn**
- **YouTube Shorts**

### Which platform should you use?

Use **Reddit** only if your account already has at least **25 karma**. Low-karma or newly created accounts may have posts filtered or receive limited distribution.

If you do not have enough Reddit karma, use **LinkedIn** or **YouTube Shorts** instead.

The platform itself does not affect scoring.

## What qualifies?

The content should be:

- technically useful,
- based on a real repository or engineering observation,
- understandable to another developer,
- evidence-driven,
- substantially based on your own reasoning, and
- useful enough that other developers would want to read, discuss, share, or respond to it.

Keep it **less promotional and more value-driven**.

The strongest entries will teach something useful even to someone who has never heard of UnvibeCode. Technical quality comes first; relevant engagement from the developer community can be used as an additional signal when comparing strong entries.

**Track 2 engagement is counted only until the challenge closes on 30 October 2026.** Engagement received after that date will not be included in judging.

## Good Track 2 examples

### LinkedIn example

Instead of:

> “Amazing AI tool! Everyone should try UnvibeCode!”

Write something closer to:

> “I analyzed an unfamiliar repository and compared the generated business workflow against the actual code. The interesting part was not the diagram—it was where static relationships stopped being enough to prove runtime behavior. Here are three things I learned…”

Then explain the technical lesson with screenshots, diagrams, or file references. A useful post should give developers something worth commenting on, sharing, or discussing—not just describe the product.

### YouTube Shorts example

A 45–60 second technical short could show:

```text
Hook:
“Can an AI really understand an unfamiliar codebase?”

→ show one UnvibeCode workflow
→ show the supporting code
→ point out one correct inference
→ point out one limitation
→ end with the engineering lesson
```

The goal is not to advertise the tool. The goal is to **teach a useful engineering idea using your analysis as evidence**.

## Avoid

- generic AI commentary,
- copying the README,
- purely promotional posts,
- unsupported technical claims,
- engagement bait,
- long AI-generated filler, or
- posts that do not show evidence that you actually used the product.

AI tools may help with editing or structure, but **your technical investigation, evidence, and conclusions should be your own**.

# 🎨 Common Five-Word Creative Challenge

After trying UnvibeCode, explain what it does in **exactly five words**.

Your line should be:

- original,
- immediately understandable,
- relevant to the product, and
- exactly five space-separated words.

Selected lines may be featured in the UnvibeCode README or social channels with participant credit.

Copied taglines, unrelated entries, and lines containing more or fewer than five words will not be considered.
